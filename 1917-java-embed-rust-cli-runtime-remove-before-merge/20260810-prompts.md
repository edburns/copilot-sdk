Here are the pros and cons:

Pros of merging into a matrix (`[default, inprocess]`):

1. Less YAML duplication — the checkout, setup-java, setup-node steps are identical across both jobs. A matrix eliminates ~20 lines of repeated boilerplate.
2. Easier maintenance — action version pin bumps happen in one place, not two.
3. Conceptual clarity — "transport mode" is just another test axis, like JDK version already is.

Cons / complications:

1. Step divergence — the `java-sdk` job has conditional steps that only run on JDK 25 (spotless, javadoc, doc-version test, JDK-17 switch). Adding `inprocess` to that matrix creates a 2×2 = 4 combinations, and inprocess+JDK17 may not make sense (native lib built for JDK 25).
2. Different `mvn` commands — inprocess runs `mvn clean verify -Pinprocess`; default runs a split build-then-test flow. Conditional `run:` blocks depending on matrix values reduce readability.
3. Failure isolation — separate jobs give independent red/green status. A matrix cell does too, but the job name becomes more complex (`Java SDK Tests (JDK 25, inprocess)`).
4. Inprocess doesn't need JDK 17 testing — the native library targets a single JDK. Folding it in would require extra `if:` guards to skip the JDK-17 leg for inprocess, partially negating the DRY benefit.

My take: A clean approach would be adding `transport: [default, inprocess]` to the existing matrix but excluding `{test-jdk: "17", transport: "inprocess"}`. The conditional steps already have `if: matrix.test-jdk == '25'` guards, so adding `&& matrix.transport == 'default'` where needed is straightforward. Net result: less duplication, minor complexity in conditionals.
