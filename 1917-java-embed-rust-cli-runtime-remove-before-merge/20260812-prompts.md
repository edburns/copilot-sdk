The reviewer is identifying a use-after-free risk at the Java/native boundary that could crash the JVM.

What “trampoline” means here

When Java passes a JNA `Callback` to native code, native code cannot directly invoke a Java lambda. JNA creates a small native-callable bridge—often called a callback trampoline—and gives Rust a C function pointer to it.

The call path is:

Rust worker thread
  → native function pointer / JNA trampoline
  → JNA attaches or enters the JVM
  → JnaNativeBinding's tracked wrapper
  → FfiRuntimeHost's original callback

The trampoline converts the native C ABI call into a Java invocation, including argument conversion and locating the corresponding Java callback object.

This is unrelated to the “trampoline” technique sometimes used to replace recursive calls. Here, it means an FFI callback stub.

The two callback objects

The code creates two distinct Java callback objects:

1. `FfiRuntimeHost` creates the original callback:

OutboundCallback callback = createOutboundCallback();
callbackRef = callback;

2. `JnaNativeBinding` wraps it:

OutboundCallback tracked = (ud, data, len) -> {
    activeCallbacks.incrementAndGet();
    try {
        callback.invoke(ud, data, len);
    } finally {
        activeCallbacks.decrementAndGet();
    }
};

It is `tracked`, not the original `callback`, that gets passed to JNA:

lib.copilot_runtime_connection_open(..., tracked, ...);

Therefore, JNA’s trampoline corresponds to `tracked`.

`FfiRuntimeHost.callbackRef` keeps the original callback alive, but it does not keep `tracked` alive. The reference direction is:

tracked → original callback

There is no reverse reference:

original callback -X→ tracked

Keeping the original callback alive consequently does not protect the wrapper or its trampoline.

Why `trackedCallbacks` exists

`trackedCallbacks` supplies the required strong Java reference:

trackedCallbacks.put(connectionId, tracked);

Without this reference, Java’s garbage collector may collect `tracked`. Native code holding its function pointer does not necessarily count as a JVM strong reference.

Once the JNA callback is collected, JNA may release the trampoline and its supporting state. If Rust later invokes the old function pointer, it calls invalid native memory. Unlike an ordinary Java exception, this can cause a segmentation fault or terminate the entire JVM.

The specific bug

On a successful connection close, the wrapper is removed immediately:

boolean closed = lib.copilot_runtime_connection_close(connectionId) != 0;
if (closed) {
    trackedCallbacks.remove(connectionId);
}

That assumes:

Once `connectionClose()` returns, native code can never invoke this callback again.

According to the reviewer, that assumption is not part of the native runtime’s current contract. Outbound work is dispatched through another queue/thread, and already-queued callback work can run after connection closure or server removal has returned.

A possible sequence is:

1. Rust queues an outbound callback.
2. Java calls connectionClose().
3. Native connectionClose() returns successfully.
4. Java removes tracked from trackedCallbacks.
5. No strong reference to tracked remains.
6. GC collects tracked and JNA releases its trampoline.
7. The queued Rust task begins executing.
8. Rust invokes the stale trampoline pointer.
9. The JVM may crash.

Why the callback counter does not fix it

Both callback counters count callbacks that have already entered Java. They do not count callbacks that are queued but have not started.

There can be a dangerous gap:

queued by Rust ─────────────── enters JNA trampoline
                    ↑
          counter still equals zero

During that gap, shutdown can observe zero and conclude everything is drained. It can then remove the strong reference just before the queued callback begins.

More importantly, the callback must enter the JNA trampoline before this executes:

activeCallbacks.incrementAndGet();

If the trampoline has already been collected, execution never safely reaches that increment. A counter inside the callback cannot protect the machinery required to enter the callback.

What the reviewer is requesting

The wrapper must remain strongly reachable for the entire period during which native code could possibly invoke its function pointer.

There are two broad solutions:

1. Change the native shutdown contract: `connection_close` or `host_shutdown` must cancel and join/drain every callback-producing queue and thread before returning. Java could then safely remove the wrapper afterward.
2. Keep callback wrappers for process lifetime: if native shutdown provides no definitive quiescence guarantee, retain every registered JNA wrapper permanently—probably in process-wide static storage—just as the native library itself is intentionally never unloaded.

    The second option leaks a small callback object per connection, but it is memory-safe. The current implementation attempts reclamation without having a reliable signal that native code is finished, which is unsafe.

1. Copy CLI bytes into the temp file.
2. Atomically move it to `cachedCli`.
3. Make `cachedCli` executable afterward.

Between steps 2 and 3, another resolver can observe a regular, nonempty final file. Because `isValidCachedFile()` checks only those properties, it returns the path and Rust attempts `Command::new(program)`, potentially failing with `PermissionDenied`/`EACCES`.

Its boolean result is ignored, and `SecurityException` is swallowed. If chmod fails, future calls continue accepting the non-executable cache entry as valid.

- Fail explicitly if that operation fails.
